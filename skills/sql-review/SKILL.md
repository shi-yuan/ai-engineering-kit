# SQL 审查 (SQL Review)

> 本文件是 ai-engineering-kit 的通用骨架版。
> 项目可在 `openspec/agent/custom-skills/sql-review/` 提供同名 Skill 覆盖本骨架
> （Skill Resolution 顺序：项目 custom-skills → 项目 skills → Kit 源），覆盖时应保留本骨架的输出格式与交互约定，只追加/替换项目特有规则。

## 定位与流程位置

本 Skill 对应人工 Code Review 节点中的 **DDL 条件子项**：

```text
变更涉及 DDL（diff 出现 DDL 脚本，或 proposal 声明数据库影响）
  → 先人工调用 sql-review，报告并入 code-review.md
变更不涉及 DDL
  → 跳过本 Skill
```

分工边界：

| 审查主体 | 审什么 |
|---|---|
| Gate 3 `change-design` | 表结构方案、迁移与回滚策略（设计期决策，避免实现后返工） |
| Gate 7 `change-review` | SQL 的业务风险：数据迁移影响、历史数据兼容 |
| `sql-review`（本 Skill） | DDL 脚本的规范与迁移风险（实现后最终把关） |

## 核心职责

审查变更涉及的 DDL 脚本（建表/改表/索引/约束/迁移），找出违反规范、存在迁移风险的地方。

**注意：只报告和给出修改建议，不直接修改 SQL 文件。**

## 通用审查清单

### 命名与注释

- 表名 / 字段名 / 索引名统一 `snake_case`，全小写加下划线；禁止中文、禁止拼音混英文。
- 索引命名：普通 `idx_<表>_<字段>`，唯一 `uk_<表>_<字段>`；约束命名：`pk_` / `uk_` / `chk_` 前缀。
- 每张表必须有表注释说明业务用途；业务字段必须有字段注释。

### 主键与唯一性

- 主键由应用层生成（雪花/号段等），禁止数据库自动生成或 UUID 作为业务主键。
- 禁止复合主键；业务唯一约束用唯一索引表达。

### 禁用项（一票否决）

- 禁止物理外键（外键由应用层维护）。
- 禁止触发器。
- 禁止物理级联删除（`ON DELETE CASCADE`）。
- 禁止 `FLOAT` / `DOUBLE` 存金额或份额（用定点 `NUMERIC`/`DECIMAL`）。
- 禁止 `SELECT *`。

### 索引合理性

- 高频 `WHERE` / `JOIN ON` / `ORDER BY` 字段必须有索引。
- 避免冗余索引；避免在低选择性字段（布尔、性别）单建索引。
- 联合索引顺序：等值条件列在前、范围列在后、排序列在最后。
- 业务唯一约束必须用唯一索引。

### 迁移脚本风险

- 大表变更：建索引使用 `CONCURRENTLY`（PostgreSQL）或 online DDL 手段，避免长时间锁表。
- 可空变更：可空改 `NOT NULL` 必须先回填数据，再加约束。
- 数据类型变更：禁止直接 `ALTER COLUMN ... TYPE`，需评估转换成本与索引重建。
- 回滚：每次迁移必须配套回滚 SQL（注释或独立文件）。
- 幂等：迁移脚本考虑可重入（`IF NOT EXISTS` / `DROP IF EXISTS`）。
- 增量管理：表结构变更必须落增量脚本，不得只改实体类。

> 项目特有的存储口径（金额/份额精度）、审计字段规范、逻辑删除约定、数据库特性差异等由项目覆盖版 Skill 定义，本骨架不重复。

## 输出格式要求

**严重问题 (P0 - 必须修复)**（缺注释/审计约束类项目红线、物理外键、金额用浮点等线上故障级问题）

**警告 (P1 - 建议修复)**（索引命名不规范、低选择性字段建索引、未用 `CONCURRENTLY` 等异味）

**优化建议 (P2 - 可选)**

**亮点**（注释完整、迁移脚本幂等、回滚齐备等）

## 交互要求

- 所有判断必须给出具体脚本 `文件路径:行号` 作为依据。
- 每个问题提供修改后的 SQL 示例或明确修改方向。
- 若审查对象不在项目约定的 DDL 目录下（如临时查询、应用代码里的 SQL 片段），先说明范围边界，再选择性应用上述规则。
- 在变更流程中执行时，报告并入 `openspec/changes/<change-id>/code-review.md` 的独立 DDL 审查段。
- 保持客观、专业，不要输出低质量的废话。
