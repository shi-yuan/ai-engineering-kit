# 代码审查 (Code Review)

> 本文件是 ai-engineering-kit 的通用骨架版。
> 项目可在 `openspec/agent/custom-skills/code-review/` 提供同名 Skill 覆盖本骨架
> （Skill Resolution 顺序：项目 custom-skills → 项目 skills → Kit 源），覆盖时应保留本骨架的输出格式与交互约定，只追加/替换项目特有规则。

## 定位与流程位置

本 Skill 对应默认变更流程中 Gate 7 `change-review` 之后的**人工 Code Review** 节点：

```text
Gate 7 Change Review（AI 审 design 一致性与业务风险）
  ↓
人工 Code Review ← 本 Skill
  ↓
Gate 8 Context Sync
```

分工边界：

| 审查主体 | 审什么 |
|---|---|
| Gate 7 `change-review` | Design 一致性、Diff 完整性、超范围修改、历史兼容、业务风险 |
| `code-review`（本 Skill） | 需求覆盖、代码层质量、Bug、性能隐患 |
| `sql-review` | DDL 脚本规范与迁移风险（变更涉及 DDL 时先于本 Skill 执行，报告并入同一评审记录） |

### 与提交前自检的关系

项目可在 apply-agent profile 中强制"提交前自检"（commit 前执行本 Skill）。
人工 Code Review 节点执行本 Skill 时，若存在提交前自检记录（通常为
`openspec/changes/<change-id>/self-check-report.md`，或 verification-report 自检节），
必须先读取并继承，不重复审查：

- 已确认的 P1/P2 结论直接继承，仅在结论变化时更新，不重复报告。
- P0 必须复核修复闭环（复跑验证），不得沿用自检结论。
- 审查聚焦自检之后的增量 Diff。
- 需求覆盖矩阵必须终核，不得直接沿用自检结果。

## 核心职责

审查代码，找出违反工程规范、存在潜在 Bug、安全漏洞或性能隐患的地方。

**注意：只报告和给出修改建议，不直接修改代码；报告经人工确认后再按最小安全变更修复。**

## 通用审查清单

### 需求覆盖度检查（最高优先级）

审查代码前，先核对变更是否完整覆盖需求或任务描述的验收标准（AC）。需求点来源：proposal、specs 或原始需求。

- 逐条比对需求点与实际代码，识别缺失功能。
- 边界条件遗漏：空值、空集合、0/最大值、并发、重复请求等场景有无处理或单测。
- 多余逻辑审查：需求未提及且无实际价值的过度设计。

### Bug 清单（通用）

- 空指针：判空缺失、Map.get 后未判空、自动拆箱 NPE、解包后 null 直接使用。
- 逻辑错误：条件分支遗漏/反转、循环边界、终止条件。
- 异常处理：吞异常、异常路径资源泄漏。
- 状态机：流转合法性、终态保护。
- 事务边界：多表写缺事务控制；事务内混入远程调用/消息发送等非事务操作。
- 并发与幂等：重复请求、重复触发下的副作用。

### 性能清单（通用）

- 循环中调库 / 调远程服务（N+1），应批量或一次查出后组装。
- 无分页或无上限的查询/导出。
- 慢查询隐患：索引未命中、大偏移分页、函数包裹列、隐式类型转换。
- 同一数据在方法与被调嵌套方法中重复查询。
- 事务持有时长被大查询/远程调用拉长。

### Engineering（通用）

- 命名与结构清晰；无魔法值；无无关重构。
- 日志与可观测性：保存/修改/删除/提交/审批/状态变更等写操作的入口和结果有日志（含业务主键或单号），外部调用、MQ 消费、Job 有日志，不打印敏感信息；关键写操作缺日志按 P1 报告。
- 测试覆盖：新增对外行为有正常/边界/异常用例。

> 项目特有的红线（金额精度、安全算法、分层架构、模块差异等）由项目覆盖版 Skill 定义，本骨架不重复。

## 输出格式要求

**严重问题 (P0 - 必须修复)**（线上故障级：资损、安全漏洞、事务缺失、数据口径违规等）

**警告 (P1 - 建议修复)**（规范异味、缺失校验、命名不一致等）

**优化建议 (P2 - 可选)**

**亮点**

**需求覆盖矩阵**（独立板块）：需求点 → 对应代码 `文件路径:行号` → 覆盖状态（已覆盖 / 部分覆盖 / 未覆盖）

## 交互要求

- 所有判断必须给出 `文件路径:行号` 作为依据。
- 每个问题给出修改示例或明确修改方向。
- 结果区分"已确认事实 / 合理推断 / 待确认问题"，不得把推断写成事实。
- 上下文无明确需求描述/验收标准时，必须暂停并追问，不得跳过需求覆盖检查。
- 在变更流程中执行时，报告落盘 `openspec/changes/<change-id>/code-review.md`（结构参照 `templates/code-review-report.md`，DDL 审查段并入同一文件）；报告末尾给出结论：

```text
PASS
PASS_WITH_NON_BLOCKING_COMMENTS
BLOCKED
```

存在 P0 未修复时必须 `BLOCKED`。
- 修复确认后按最小安全变更实施，不夹带无关重构；P0 修复后复跑本 Skill 复核。
- 保持客观、专业，不要输出低质量的废话。
