# 接口实测骨架 (API Verification)

> 本 Skill 为通用骨架。**项目 custom-skills 同名 Skill 优先覆盖**（`resolve-skill` 解析顺序：
> custom-skills → 项目 skills → kit skills）。项目接入时必须先完成"第 0 节 项目适配点"的登记，
> 否则禁止执行接口实测（一律 BLOCKED）。
>
> **协议边界**：本骨架的默认实现形态是 HTTP/OpenAPI（springdoc/swagger）。其他 RPC 形态的项目
> （Dubbo、gRPC、纯内部 Feign 等）仍用同名 Skill 挂接 Gate 6，但在项目 custom-skills 同名实例中
> **整体替换实现**（如 Dubbo 泛化调用 `GenericService`、dubbo-admin 元数据比对、消费侧直连验证）；
> 必须保持不变的是：适配点登记模式、Gate 6 产物约定（报告归档路径、verification-report 引用、
> 结论枚举 PASS/PASS_WITH_MANUAL_CHECKS/FAIL/BLOCKED）与安全红线（凭证红线、禁止伪造结果）。

## 0. 项目适配点（项目实例必须登记，缺失即 BLOCKED）

项目实例（custom-skills 同名 SKILL.md）须明确以下事实，本项目未登记的一律不得假设：

1. **服务地址表**：各服务本地端口、API 路径前缀、`/v3/api-docs` 地址、API 文档 UI（如 swagger-ui/knife4j）。
2. **鉴权约定**：外部接口鉴权方式（token 类型、携带方式 header/cookie）、免登录内部接口前缀、
   **凭证本地文件路径**（单行纯凭证；禁止入库、禁止写入任何 artifact，报告中一律脱敏）。
3. **统一响应判定**：统一响应体结构与业务成功码（HTTP 200 ≠ 业务成功，必须双条件判定）。
4. **测试数据约定**：测试数据可识别标记（便于事后清理），可复用的既有测试数据位置
   （testdata 目录、既有 .http 文件、业务键登记文档）。
5. **环境前提**：服务如何本地启动、连哪个环境的数据/配置中心，脏数据是否可接受。
6. **输出目录约定**：有变更上下文时 `openspec/changes/<change-id>/`；无变更上下文时的落点
   （如需求目录），两者都无则询问用户。

## 1. 执行流程

### Step 0 确定测试范围

模式判定：用户**点名了具体接口清单** → `LISTED`；用户要求全量回归 → `FULL`；其余（含用户只说
"实测本次改动接口"）→ 默认 `TARGETED`。

- **TARGETED（默认）**：只测本次变更**新增或改动**的接口，来源为变更的 proposal/design/tasks +
  `00-change-analysis.md` 中的接口清单；未列出的既有接口不生成用例、不执行。
- **LISTED**：用户点名接口（如提供 swagger 地址 + 接口清单）。严格只测点名清单，超出清单的接口
  只做契约比对（Step 2），不生成用例、不调用。点名的接口按路径/方法模糊匹配 api-docs；命中多个
  或不命中时向用户确认，不猜。
- **FULL**：仅用户明确要求全量回归时使用，覆盖目标服务全部外部接口；内部免登录接口仅在涉及
  Job/回调改动时纳入。

范围与模式必须写入报告，禁止默认跑全量。

### Step 1 拉取契约

- 用户显式提供的 swagger/api-docs 地址**优先**于项目登记的服务地址表；未提供时按登记表，
  拉取失败时不得改用臆造的地址。
- 拉取 `/v3/api-docs`，保存快照到 `openspec/changes/<change-id>/api-docs-snapshot.json`。

### Step 2 契约比对

- **基线策略**：判定"意外变更"需要变更前契约做基线，按优先级取：
  1. 测试环境部署实例的 `/v3/api-docs`（其代码版本为变更前时可直接作基线，执行前确认版本）；
  2. 改动代码之前留存的快照；
  3. 无可用基线：只做"存在性 + 当前签名与 design/tasks 一致性"核对，并在报告中**明确注明
     无基线、无法判定历史接口意外变更**，不得装作比对过。
- 本次涉及接口必须在 api-docs 中存在且签名一致；基线比对发现已有接口签名被意外变更必须报告。

### Step 3 生成用例

生成 `api-verification.http`（格式沿用项目内既有 .http 惯例），要求：

- 数据来源：优先复用项目已沉淀的测试数据与业务键（见适配点 4）；造新数据用可识别标记，便于清理。
- 覆盖场景：正常、边界、异常（参数非法/不存在/状态不允许）、重复提交（幂等）。
- 写接口必须有前置查询确认初始状态，验证后回查确认终态；有依赖的接口按业务顺序编排。
- **参数解析链（按序降级，任何一级都不得臆造业务键）**：
  1. **契约层**：api-docs schema + DTO 字段语义（枚举、格式、长度约束）。
  2. **知识层**：项目已沉淀事实（业务键登记、变更分析、需求文档、既有 .http、testdata）。
  3. **依赖链层**：参数来自其他接口/服务的，先调前置查询接口实时取值，禁止手编业务键；
     前置查询纳入用例矩阵（setup 步骤），取值路径记录在用例注释中。
  4. **人工层**：仍不确定的必填参数两选一：弹窗询问获取真实取值；或 `.http` 中用 `<<TODO:说明>>`
     占位并标注 `[BLOCKED-占位]` 跳过执行，报告"未覆盖项"列出占位符清单等回填。
  可选参数不确定时一律省略，不猜默认值。

### Step 4 执行

- 逐条执行（凭证从本地凭证文件注入），设置合理超时（慢接口调大），不得绕过逐条记录。
- **响应原文落盘**：`openspec/changes/<change-id>/api-responses/<序号>-<用例名>.json`；
  报告摘要为截断引用，含敏感字段（手机号/姓名/证件等）的响应摘要时脱敏。
- 每条记录：用例名、HTTP status、业务码、msg、响应摘要、耗时、结论（PASS/FAIL/BLOCKED）。
- **幂等用例判定**：先从 design 与状态机登记确认预期——第二次请求被幂等/状态拦截返回业务错误码
  = PASS；产生第二条记录或状态被重复推进 = FAIL。
- FAIL 后先分析原因，修正用例可重跑，FAIL 历史保留在报告中。
- 服务重启、配置中心断连、凭证过期 → 当前项 BLOCKED，如实记录。
- **数据收尾**：本轮造出的带标记数据在用例链允许范围内清理；无法清理的列入报告"残留数据清单"
  （对象 + 业务键 + 产生用例）。

### Step 5 输出报告

输出 `api-verification-report.md`，并在 `verification-report.md` 的 API 实测小节引用结论。报告至少包含：

- 环境信息（服务、执行时间、凭证有效性——不含凭证本身；基线来源与版本说明）。
- 契约比对结论（新增/变更/意外变更的接口清单；无基线时如实注明）。
- 用例执行矩阵：用例 × 场景类型 × 结果 × 证据（指向落盘文件）。
- 失败与阻塞项：原因、影响、风险、后续动作。
- 未覆盖项（外部触达类接口、占位符待回填用例）。
- 残留数据清单。
- 最终结论：`PASS / PASS_WITH_MANUAL_CHECKS / FAIL / BLOCKED`。

## 2. 安全边界与禁止事项

- 写操作是否允许自动执行、哪些操作必须人工确认（外部系统触达、删除存量数据、资金终态流转等），
  以项目实例登记为准；骨架默认对以上三类停下询问。
- 接口行为与需求/设计语义不符时如实报告，**不得修改代码来"让用例通过"**；修代码回正常 Gate 流程。
- 不得伪造未执行的调用结果；不得把 HTTP 200 当业务成功。
- 不得把凭证写入任何 artifact 或日志输出。
- 不得调用 api-docs 中不存在、或路径/方法未经确认的接口。
- 不得因单条 FAIL 中断全部流程而丢弃剩余用例结果（除非前置依赖被破坏）。
- 不得把测试环境调用结果当作生产环境结论。
