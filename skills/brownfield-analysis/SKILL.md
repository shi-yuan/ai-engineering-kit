# Brownfield Analysis

## 目标

在 OpenSpec propose/design
之前，对已有系统进行代码考古，生成基于证据的变更分析。

本 Skill 主要用于：

-   历史功能修改；
-   多模块或多仓改造；
-   存在隐式业务规则的逻辑；
-   "这里改一点、那里联动一块"的需求。

本 Skill 不负责生成 Design，也不修改生产代码。

## 输入

-   聚合工作目录
-   `.agent-env.md`
-   当前需求目录
-   `<OPEN_SPEC_ROOT>/project-context/`
-   相关实现仓库

## 输出

在当前需求目录生成或更新：

`20-change-analysis.md`

必须使用 `templates/change-analysis.md` 的主体结构。

## 执行步骤

### 1. 建立工作区事实

读取 `.agent-env.md`，解析 `OPEN_SPEC_ROOT`。

读取：

-   `system-overview.md`
-   `architecture.md`
-   `module-map.md`
-   `data-model.md`
-   相关业务流程
-   相关业务不变量

读取当前需求目录全部相关文件。

用简洁语言重新描述"需求真正要改变什么"。

不要把推测写成事实。

### 2. 查找真实入口

识别已有行为从哪里触发，例如：

-   API 或页面请求
-   RPC 或其他跨进程调用
-   消息消费
-   定时任务
-   批处理
-   Callback / Webhook
-   运维或管理命令

必须通过代码搜索确认真实类、方法和文件路径。

### 3. 端到端追踪当前行为

从入口追踪到最终副作用。

重要分支必须继续查看调用方和被调用方，禁止只读一个方法。

至少关注：

-   业务判断
-   持久化查询和更新
-   状态变化
-   外部调用
-   异步边界
-   配置分支
-   重试和补偿
-   事务边界
-   锁、幂等和并发控制
-   异常路径和边界路径

遇到跨仓调用或异步消息时，继续追踪另一端。

### 4. 发现隐式业务规则

重点检查容易被 AI 错误解释的语义：

-   `0`、负数、`null`、空集合、特殊枚举值
-   状态流转
-   排序和先后顺序
-   分页和批处理语义
-   部分成功
-   历史兼容分支
-   重试和重复处理
-   金额、余额、库存、额度等不变量
-   注释与命名不一致
-   测试中存在但文档未描述的业务规则

不得根据单一线索直接声明业务不变量。

### 5. 确定影响范围

明确区分：

-   确定受影响
-   可能受影响，需要 Design 决策
-   已检查但不受影响

根据 `module-map.md` 检查所有相关仓库。

### 6. 记录证据和不确定性

重要结论应记录代码证据，例如：

`xyy-pop-business/src/.../PopCashAdvanceService.java#deductOnlineApplyAmount`

统一使用以下分类：

-   `已验证事实`
-   `需求变化`
-   `假设`
-   `待确认问题`

如果继续搜索代码可以回答，就继续调查，不要过早询问人工。

### 7. 生成 Change Analysis

生成 `20-change-analysis.md`。

文档必须让"另一个没有当前对话上下文的 Agent"可以继续做 Design。

完成前执行：

`references/analysis-checklist.md`

## 阻断条件

出现以下情况，不得进入 OpenSpec propose/design：

-   主执行链路没有追踪清楚；
-   找不到关键实现仓库；
-   关键业务分支仍完全依赖猜测；
-   project-context 与代码存在重大冲突但未记录；
-   已知存在跨进程或异步依赖，却未检查另一端。

无法确认时，明确输出未解决项，不得伪造完整分析。
