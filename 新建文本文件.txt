2、做一个需求时怎么跑
    假设需求是：提现时优先扣减在线支付可提现金额，不足部分使用商户余额补充
    先定一个 Change ID：withdraw-online-amount-refactor

    Step 1：brownfield-analysis
        按照 AI Engineering Kit 的 brownfield-analysis Skill 分析当前需求。

        Change ID：
        withdraw-online-amount-refactor

        需求：
        提现时优先扣减在线支付可提现金额，不足部分使用商户余额补充。

        要求：
        1. 读取 AGENTS.md、.agent-env.md、openspec/config.yaml。
        2. 读取 openspec/agent/project-rules.md、相关 rules、相关 project-context。
        3. 以 WORKSPACE_ROOT 为代码搜索边界，分析所有相关仓库。
        4. 只分析，不修改业务代码。
        5. 输出到：
           openspec/changes/withdraw-online-amount-refactor/00-change-analysis.md

    人工 Review 00-change-analysis.md，重点看：
        入口找全了吗
        涉及仓库找全了吗
        表、字段、状态、金额语义清楚了吗
        RPC / MQ / Job / Redis / Apollo 有没有漏
        事实、推断、待确认问题有没有区分

    Step 2：OpenSpec propose（确认分析靠谱后，再让 Agent 基于分析创建 OpenSpec change）
        基于当前需求和 openspec/changes/withdraw-online-amount-refactor/00-change-analysis.md，
        创建 OpenSpec proposal / spec delta / tasks。

        要求：
        1. 不要重新猜测业务语义。
        2. 必须引用 00-change-analysis.md 中的现状、影响范围和风险。
        3. Proposal 必须覆盖涉及仓库、数据库、接口、RPC、MQ、Job、兼容性和风险。

    Step 3：change-design
        基于 00-change-analysis.md、proposal、specs、tasks，
        完成当前 Change 的 design。

        重点说明：
        1. 当前行为。
        2. 目标行为。
        3. 最小安全变更方案。
        4. 数据变化。
        5. 调用链变化。
        6. 事务、并发、幂等、重试、补偿。
        7. 历史数据兼容。
        8. 回滚方案。

    Step 4：design-review（如果是 BLOCKED，不要进入实现，回到 design 修）
        按照 design-review Skill 审查当前 Change。

        Change ID：
        withdraw-online-amount-refactor

        读取：
        00-change-analysis.md
        proposal
        specs
        design
        tasks
        相关 project-context
        相关 rules
        相关业务代码

        只审查，不修改业务代码。

        最终结论使用：
        PASS
        PASS_WITH_NON_BLOCKING_COMMENTS
        BLOCKED

    Step 5：人工 Review（人工确认后再进入 apply）
        系统理解是否正确
        影响范围是否完整
        设计是否过度
        兼容策略是否安全
        测试和验证是否足够

    Step 6：OpenSpec apply
        按照已通过 Review 的 OpenSpec Change 实现代码。

        Change ID：
        withdraw-online-amount-refactor

        严格依据：
        00-change-analysis.md
        proposal
        specs
        design
        tasks

        要求：
        1. 不得擅自扩大范围。
        2. 不得做无关重构。
        3. 如果发现真实代码与 design 冲突，停止冲突部分并报告，不要自行改设计继续写。

    Step 7：verification
        按照 verification Skill 验证当前 Change。

        Change ID：
        withdraw-online-amount-refactor

        检查：
        Requirement Coverage
        Design Conformance
        Build
        Test
        核心场景
        边界场景
        异常场景
        重复请求
        重复消费
        重复 Job
        并发
        历史数据兼容

        输出：
        openspec/changes/withdraw-online-amount-refactor/verification-report.md

        不得伪造未执行的验证结果。

    Step 8：change-review
        按照 change-review Skill 审查当前 Change。

        Change ID：
        withdraw-online-amount-refactor

        基于所有相关仓库实际 Diff 审查。

        重点检查：
        遗漏修改
        超范围修改
        历史兼容
        SQL
        金额精度
        事务
        并发
        锁
        幂等
        RPC
        MQ
        Job
        日志
        测试
        文档同步

        最终结论使用：
        PASS
        PASS_WITH_NON_BLOCKING_COMMENTS
        BLOCKED

    Step 9：OpenSpec archive
        最后归档前检查，如果这次需求沉淀出了长期有效的业务事实，就更新 project-context 或 rules；
        单次需求细节留在 changes/<change-id> 里。
        openspec/project-context/
        openspec/rules/
