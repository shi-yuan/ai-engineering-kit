# 测试与验证规则

## 适用范围

所有变更都适用；历史功能增强和高风险核心变更必须严格执行。

## 必须覆盖

- Requirement Coverage。
- Design Conformance。
- 编译或静态检查。
- 单元测试、集成测试或替代验证。
- 需要容器语义（鉴权、序列化、实际 SQL、中间件联动、跨服务链路）的验证项，优先走接口实测
  （Skill：`api-verification`；项目须在 `custom-skills` 提供同名实例登记服务地址、鉴权、
  统一响应等适配点后启用），无法实测的列为人工检查项。
- 核心正常场景。
- 边界场景。
- 异常场景。
- 重复请求、重复消费、重复 Job。
- 并发和幂等。
- 历史数据兼容。
- 多仓库修改完整性。

## 禁止事项

- 不得伪造未执行的编译、测试、SQL、环境验证结果。
- 不得只验证 happy path。
- 不得把“代码已实现”当作验证完成。
- 不得忽略未验证项；无法执行时必须说明原因、风险和 Owner。

## Verification Report 要求

`verification-report.md` 至少包含：

- 验证结论。
- 受影响仓库和 Diff。
- 已执行检查和证据摘要。
- 未执行检查、原因、风险、后续动作。
- 关键业务场景。
- 风险场景。
- 人工检查项。
- Context Sync 建议。

## 高风险变更要求

涉及资金、库存、授信、合同、权限、计费、清结算、履约等高风险场景时，必须额外覆盖：

- 幂等。
- 状态终态保护。
- 重试和补偿。
- 对账或审计。
- 回滚后兼容。
