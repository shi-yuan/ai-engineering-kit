# 代码结构规则（Service 层职责拆分）

## 适用范围

适用于采用 `controller / service(+impl) / mapper` 分层、Service 实现类容易膨胀的项目
（Java + Spring 生态常见）。纯函数式/脚本类项目可忽略本规则。

## 命名

- 业务校验器：`XxxValidator`，**不加动作动词前缀**（不要 `XxxSaveValidator`、`XxxCheckValidator`，
  动作属于调用场景，不是类的本质职责）。
- 对象转换：`XxxConverter`，只放静态方法、不持有状态，禁止在 Service 实现类里重复手写 set 转换。
- 注解式校验器（JSR-303 等）同样以 `XxxValidator` 命名。

## 放置位置：按项目既有约定，先查再放

- 新增校验器/转换器前，必须先用 `*Validator` / `*Converter` 搜索本项目已有位置，**从众放置**。
- 不得新造包名，不得照搬其他模块或示例项目的包路径。
- 多模块项目中各模块包名可能不统一（`util` 与 `utils`、`validation` 与 `service.validator` 并存），
  属历史约定；新代码从众，不做跨模块"顺手统一"。

## Service 层职责边界

Service 实现类只做**流程编排**，以下逻辑不得堆积在类内：

| 逻辑类型 | 归属 |
|---|---|
| 复杂业务校验（多字段互斥、跨表校验、规则组合） | `XxxValidator`，无状态、构造器注入 |
| 入参/出参转换（Req ↔ Entity ↔ Res、枚举转义） | `XxxConverter` 静态方法 |
| 分布式锁、缓存、幂等、发号等技术设施 | 复用团队公共库（见"禁止自研"） |

- 校验器/转换器不得反向依赖 Service 实现类（避免循环依赖）。
- 一个业务域原则上：1 个 Service 接口 + 1 个实现 + 1 个 Validator + 1 个 Converter；
  超出说明职责划分需要重新评估。

## 类规模预警（阈值按项目实际调整）

- 新增 Service 实现类超过**约 600 行**必须评估拆分；超过**约 800 行**视为必须拆分，
  提交前给出拆分方案。
- 拆分方向：业务校验 → Validator；对象转换 → Converter；领域计算 → 领域组件；
  外部协作 → 独立 Client/Gateway。
- 历史超大类属遗留债务，修改时按最小变更原则处理，不强制一次性重构。

## 禁止自研技术设施

- 分布式锁、缓存、幂等、发号、序列化等基础设施，优先复用团队/公司公共库。
- **禁止**自建锁表、裸 `SELECT ... FOR UPDATE` 自创互斥方案，或在业务模块内重新实现公共库已提供的能力。
- 如确需自研，必须在 Design 中说明公共库为何不满足，并记录评估结论。

## AI 生成代码的结构复查（apply 阶段）

- AI 生成的 Service 实现类视为**草稿**：功能跑通不等于结构合格。
- 提交前必须检查四类问题：校验逻辑内联、转换代码重复、类行数超阈值、自研基础设施。
- 结构问题在 apply 阶段修掉，不留到后续需求；修复后复跑 code-review 确认。

## Design / Verification 要求

- Design 写明本需求的类职责划分：入口、编排、校验、转换、外部协作。
- Verification 记录拆分结果（各类行数与职责）；未拆分需说明理由。
- 涉及锁/缓存选型时记录所用工具类与关键参数策略。
