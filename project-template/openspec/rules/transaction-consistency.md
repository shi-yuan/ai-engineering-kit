# 事务与一致性规则

## 适用范围

涉及状态变化、核心数值变化、跨库、RPC、MQ、Job、缓存、外部系统调用、补偿、最终一致性时适用。

## 必须检查

- 本地事务边界。
- 外部调用发生在事务内还是事务外。
- MQ 发送时机。
- 状态 CAS 或乐观锁。
- 分布式锁、Redis 锁、数据库唯一键。
- 重复请求、重复消费、重复 Job。
- 失败补偿和最终一致收敛路径。
- 回滚后新旧数据兼容。

## 禁止事项

- 不得把外部调用和本地事务假定为原子操作。
- 不得在无幂等保护时增加重试。
- 不得删除状态保护条件。
- 不得让补偿任务和实时链路互相覆盖终态。
- 不得吞掉异常而没有日志、告警或补偿。

## Design 要求

Design 必须说明：

- 哪些操作在同一事务内。
- 哪些操作是最终一致。
- 幂等键和状态保护。
- 重试、补偿和人工修复路径。
- 异常场景下系统如何收敛。

## Verification 要求

- 重复请求。
- 重复消息。
- 重复 Job。
- 并发更新。
- 外部超时、失败、回调乱序。
- 补偿任务重复执行。

## 事务宽度（Service 编排方法）

**原则：事务内只放 DB 写语句。事务宽度不等于方法宽度。**

- 短 CRUD 写方法（几条语句、无外部协作）：默认 `@Transactional(rollbackFor = Exception.class)` 即可。
- **编排型方法（校验 + 转换 + 锁 + RPC + 写库）禁止整个方法加 `@Transactional`**——
  校验、RPC、锁等待全部落入事务会形成长事务：占用连接池、放大锁竞争与回滚范围。
- 事务外处理：复杂校验/转换（抽 Validator/Converter）、RPC 调用、Redis 锁等待、
  异步通知（走 Outbox/消息）。
- 顺序约定：**先取锁 → 开事务写 → 提交 → 释放锁**；锁必须覆盖提交窗口，禁止提交前释放。
- 收窄手段：拆出窄写方法加注解（注意 Spring 自调用陷阱——同类内部调用注解不生效），
  或 `TransactionTemplate.execute` 显式包写段（需核对写段完整性，段外写语句不会回滚）。
- AI 生成的编排方法常默认整方法加 `@Transactional`：提交前必须做事务宽度复查。
- 不批量改造存量宽事务；触碰相关类时按本节复查。
